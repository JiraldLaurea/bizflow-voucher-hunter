# Localisation

English, Korean, Chinese, Japanese. English is the source of truth and the
fallback for any missing key.

Three independent catalogues, deliberately not merged: the **mobile app** (the
customer UI), the **business landing page** (`/`, marketing prose for owners)
and the **customer landing page** (`/client`, the same product described to the
person who downloads the app). They share the language set and the fallback rule
but almost no strings, and combining them would put the wrong tone one line away
from the right one.

| | Mobile app | Landing pages |
|---|---|---|
| Copy | `apps/mobile/src/i18n/translations.ts` | `src/i18n/marketing.ts` (`/`), `src/i18n/client.ts` (`/client`) |
| Lookup | `useTranslation()` hook | `translator(language)` / `clientTranslator(language)` — no hook, no context |
| Choice stored in | SecureStore | the `vh_lang` cookie |
| Selector | `components/LanguagePicker.tsx`, in More | `app/_components/LanguageSelector.tsx`, in the nav of both pages |

The web's language set, fallback rule and shared lookup live in
`src/i18n/languages.ts`, so neither web catalogue is the other's dependency.

**The vocabulary is shared across all three** even though the strings are not.
Loyalty Points / LP, voucher, campaign and partner shops must read the same in
the app and on both pages; change a term in one catalogue and change it in the
others.

# Mobile app localisation

## How it works

| Piece | Where |
|---|---|
| Copy for all four languages | `apps/mobile/src/i18n/translations.ts` |
| Provider, `useTranslation()`, persistence | `apps/mobile/src/i18n/LanguageContext.tsx` |
| Selector UI | `apps/mobile/src/components/LanguagePicker.tsx` (rendered in More) |

```tsx
const t = useTranslation();
<Text>{t("more.title")}</Text>
<Text>{t("more.signedInAs", { phone })}</Text>   // {placeholders} interpolate
```

**Which language is used**, in priority order:

1. The choice stored in SecureStore, if the user has ever picked one.
2. The device language, when it is one of the four.
3. English.

**A missing key falls back to English**, not to a raw key or a blank, so an
untranslated string reads as untranslated rather than as broken.

## Why there is no language step on first launch

It was considered and deliberately left out. A Korean phone already opens the
app in Korean because of the device-language default, so a first-run picker
would be a gate that nearly every user dismisses without reading — friction
before any value, for a setting that is already right. The selector in More
covers the cases the default misses: a phone set to a language we do not carry,
a shared device, or simply a preference that differs from the OS.

Revisit this if analytics ever show people hunting for the language setting.

## Translation status

**The ko / zh / ja strings have not been reviewed by a native speaker.** They
are internally consistent and fine for testing, but the product vocabulary
carries meaning that a translator should confirm before a public launch:

- *voucher* — a promotional discount, not a gift certificate or a coupon book
- *Loyalty Points (LP)* — a program unit, never money. The Play "financial
  features" declaration rests on this distinction; see PLAY_CONSOLE_ANSWERS.md §8
- *hunt* — the reveal mechanic, deliberately playful and deliberately not
  gambling vocabulary; see PLAY_CONSOLE_ANSWERS.md §4
- *reserve / slot* — a booked visit window, not a queue position

## Coverage

**Complete.** Every customer-facing screen and shared component is translated:
tab bar, sign-in, home, the full campaign flow (landing, roulette, results,
date/time, confirm, confirmation), vouchers list and detail, More including
Loyalty Points, plus `ErrorState`, `NotificationSettings`, `HuntUi`,
`VoucherTicket`, `RouletteReel`, `LoyaltyAwardModal` and `Screen`.

Deliberately **not** translated:

- **"Voucher Hunt"** — the brand name, in the campaign app bar and `BrandMark`.
- **`dev/DevToolsPanel.tsx`** and the `Select` placeholder it relies on — never
  renders outside development.
- **`(tabs)/more.tsx`** — the file is a commented-out legacy screen kept as
  migration history; the route is a one-line re-export of `MoreScreen`.

To verify nothing has regressed, this should return only the brand name and the
commented-out legacy block:

```bash
cd apps/mobile/src
grep -rnE '>[A-Z][a-z][^<>{}]{4,}<|(label|placeholder|title|subtitle|fallback|accessibilityLabel|accessibilityHint|loadingLabel|detail|footnote)="[A-Z][^"]{3,}"' \
  --include=*.tsx . | grep -v './dev/\|./i18n/\|LanguagePicker'
```

### Adding a string

Add the key to all four catalogues in `translations.ts` (TypeScript enforces
this — a catalogue missing a key fails the build), then `t("your.key")` in the
component. Note that `t` changes identity when the language changes, so it
belongs in any `useCallback`/`useEffect` dependency array that uses it.

# Landing page localisation

Both landing pages are translated — `/` for businesses and `/client` for
customers. Nothing else on the web is: the dashboard, the login page,
`/privacy` and the campaign flow are all still English only.

## How it works

They stay **server components**. `translator(language)` — `clientTranslator()`
on `/client` — returns a plain `t(key)` function, so rendering a string involves
no context and no client JavaScript; only the requested language is ever sent to
the browser. The one piece of client code is the selector itself, which writes
the cookie and calls `router.refresh()` to re-render on the server.

```tsx
const t = translator(language);
<h1>{t("hero.title")}</h1>
```

The cookie is shared, so switching language on one page carries to the other —
which is the point: a Korean visitor who follows "For Clients" from the business
page lands on a Korean customer page.

**Which language is used**, in priority order — the same shape as the mobile
rule, resolved in `src/lib/locale.ts`:

1. The `vh_lang` cookie, if the visitor has ever used the selector.
2. The browser's `Accept-Language`, when it names one of the four.
3. English.

So a Korean browser gets Korean copy without touching anything, and the selector
covers what that misses.

`lang` is set on the page's root `<div>` rather than on `<html>`, because the
root layout is shared with every other route and reading a cookie there would
make the whole site dynamic for one attribute.

## What is deliberately not translated

- **"Voucher Hunt"** — the brand name, in the nav and footer wordmarks.
- **The support email address.**
- **Campaign titles, business names and category labels** — tenant data, shown
  in whatever language the business entered it in.
- **The selector's own `aria-label`** — a screen reader user who has landed in
  the wrong language needs it findable, and the four language names beside it
  are already self-describing.

## Adding a string

Add the key to all four catalogues in the file for that page —
`src/i18n/marketing.ts` for `/`, `src/i18n/client.ts` for `/client` (TypeScript
enforces this — a catalogue missing a key fails the build), then use
`t("your.key")` in the component.

Copy that is a list — the three steps, the three app screens — keeps its keys in
an array in the page and its strings in the catalogue, so a translator never has
to step around an icon import.

## Server-side copy is not localised

SMS bodies and API error messages are generated by the backend, which has no
notion of the user's language — the OTP text and the voucher confirmation are
English regardless. Localising those means passing a language with the request
and translating in `src/server/`, which is a separate piece of work.
